Exploitation Summary

The target machine was running Wing FTP Server v7.4.3 on the virtual host ftp.wingdata.htb, which is vulnerable to CVE-2025-47812, an unauthenticated remote code execution vulnerability. By exploiting this CVE with a public proof-of-concept, I gained a shell as the wingftp system user.

Inside the Wing FTP installation directory, I found salted SHA-256 password hashes for the wacky user. After identifying the salt string used (WingFTP) from the service configuration files, I cracked the hash with Hashcat in mode 1410 and pivoted to wacky, obtaining the user flag.

Privilege escalation was achieved through a Python tarfile arbitrary file write vulnerability, CVE-2025-4517. The wacky user could run a backup restore script as root via sudo, which used tarfile.extractall() with filter="data". By crafting a malicious tarball that chains symlinks exceeding the kernel's MAX_PATH limit, I bypassed the filter validation and wrote an arbitrary file to /etc/sudoers.d/wacky, granting full sudo access and thus root.

Technologies/Exploits: Wing FTP Server unauthenticated RCE (CVE-2025-47812), Hashcat salted SHA-256 cracking (mode 1410), Python tarfile arbitrary file write via symlink chain bypass (CVE-2025-4517).

Privilege Escalation — Python tarfile Arbitrary File Write (CVE-2025-4517)

Analysing the sudo Permission

Checking wacky's sudo rights:

    (root) NOPASSWD: /usr/local/bin/python3 /opt/backup_clients/restore_backup_clients.py *

The wacky user can run a specific Python backup restore script as root. Let's read it:

#!/usr/bin/env python3
import tarfile
import os
import sys
import re
import argparse

BACKUP_BASE_DIR = "/opt/backup_clients/backups"
STAGING_BASE = "/opt/backup_clients/restored_backups"

def validate_backup_name(filename):
    if not re.fullmatch(r"^backup_\d+\.tar$", filename):
        return False
    client_id = filename.split('_')[1].rstrip('.tar')
    return client_id.isdigit() and client_id != "0"

def validate_restore_tag(tag):
    return bool(re.fullmatch(r"^[a-zA-Z0-9_]{1,24}$", tag))

def main():
    ...
    staging_dir = os.path.join(STAGING_BASE, args.restore_dir)
    os.makedirs(staging_dir, exist_ok=True)
    try:
        with tarfile.open(backup_path, "r") as tar:
            tar.extractall(path=staging_dir, filter="data")
    except (tarfile.TarError, OSError, Exception) as e:

        sys.exit(2)

The script accepts a -b (backup filename) and a -r (restore directory name) argument, validates both with regex, and then calls tarfile.extractall(path=staging_dir, filter="data"). The key constraint is write access: I cannot write to /opt/backup_clients/ itself, but I do have write access to /opt/backup_clients/backups/, where the tarballs are read from.

Why Symlink Attacks Are Blocked by filter="data"

The first idea is to craft a tarball containing symlinks pointing outside the extraction directory. For example:

ln -s ../../../../../../../etc/shadow shadow_relative
ln -s /etc/shadow shadow_absolute
tar -cf backup_1.tar shadow_relative
tar -cf backup_2.tar shadow_absolute
[!] Error during extraction: 'shadow_relative' would link to '/etc/shadow', which is outside the destination
[!] Error during extraction: 'shadow_absolute' is a link to an absolute path

Both attempts are blocked. This is expected behaviour of filter="data", documented in PEP 706:

"Refuse to extract links (hard or soft) that link to absolute paths. Refuse to extract links (hard or soft) which end up linking to a path outside of the destination."

No other obvious injection vector exists in the script, so the focus shifts to finding a CVE in the tarfile library itself.

Finding the Right CVE

Checking the Python version:

python3 --version
Python 3.12.3

My first finding is CVE-2024-12718, but that only provides a useful primitive when filter="tar" is used. With filter="data" the impact is limited to metadata changes, which isn't useful here.

Searching further, I find a more recent vulnerability: CVE-2025-4517, and a Google Security Research advisory with a working PoC: GHSA-hgqp-3mmf-7h8f. This one allows arbitrary file writes even with filter="data".

Understanding CVE-2025-4517

The vulnerability is rooted in how filter="data" validates symlink chains against the kernel's MAX_PATH (4096 characters on Linux). The filter calls os.path.realpath() to resolve the full chain, but realpath() silently truncates resolution once it hits MAX_PATH — it stops following links and returns an incomplete, inaccurate path. The filter then sees a path that appears to land within the staging directory and considers it safe.

The attack works by chaining multiple symlinks, each with a long target path (~247 chars), across approximately 16 levels totalling ~3952 characters. The structure looks like:

a → ddddddd...ddd (247 chars)
└─ b → ddddddd...ddd (247 chars)
   └─ c → ddddddd...ddd (247 chars)
      └─ ... (16 levels, ~3952 chars total)
         └─ final → /etc/sudoers.d/wacky (target privileged file)

When the filter resolves the chain with os.path.realpath(), it exhausts MAX_PATH partway through and stops — never reaching the actual target. It considers the path valid and extraction proceeds. At runtime, the kernel then follows the full, real symlink chain and writes to the privileged file.

Building and Executing the Exploit

El script acepta un argumento -b (nombre del archivo de backup) y un -r (nombre del directorio de restauración), valida ambos con regex y llama a tarfile.extractall(path=staging_dir, filter="data"). La restricción clave es el acceso de escritura: no puedo escribir en /opt/backup_clients/ en sí, pero sí tengo permisos de escritura en /opt/backup_clients/backups/, donde se leen los tarballs.

Por qué los Ataques de Symlink los Bloquea filter="data"

La primera idea es crear un tarball con symlinks apuntando fuera del directorio de extracción. Por ejemplo:

ln -s ../../../../../../../etc/shadow shadow_relative
ln -s /etc/shadow shadow_absolute
tar -cf backup_1.tar shadow_relative
tar -cf backup_2.tar shadow_absolute
[!] Error during extraction: 'shadow_relative' would link to '/etc/shadow', which is outside the destination
[!] Error during extraction: 'shadow_absolute' is a link to an absolute path

Ambos intentos son bloqueados. Es el comportamiento esperado de filter="data", documentado en PEP 706:

"Refuse to extract links (hard or soft) that link to absolute paths. Refuse to extract links (hard or soft) which end up linking to a path outside of the destination."

No hay otro vector de inyección obvio en el script, así que el enfoque pasa a buscar un CVE en la propia librería tarfile.

Encontrando el CVE Adecuado

Compruebo la versión de Python:

python3 --version
Python 3.12.3

Mi primer hallazgo es CVE-2024-12718, pero solo proporciona un primitivo útil cuando se usa filter="tar". Con filter="data" el impacto se limita a cambios de metadatos, lo que no sirve aquí.

Siguiendo la búsqueda, encuentro una vulnerabilidad más reciente: CVE-2025-4517, y un advisory de Google Security Research con una PoC funcional: GHSA-hgqp-3mmf-7h8f. Éste permite escrituras arbitrarias de archivos incluso con filter="data".

Entendiendo CVE-2025-4517

La vulnerabilidad reside en cómo filter="data" valida las cadenas de symlinks frente al MAX_PATH del kernel (4096 caracteres en Linux). El filtro llama a os.path.realpath() para resolver la cadena completa, pero realpath() trunca silenciosamente la resolución al alcanzar MAX_PATH — deja de seguir enlaces y devuelve un path incompleto e inexacto. El filtro entonces ve un path que parece estar dentro del directorio de staging y lo considera seguro.

El ataque funciona encadenando múltiples symlinks, cada uno con un path destino largo (~247 caracteres), en unos 16 niveles que suman ~3952 caracteres. La estructura es la siguiente:

a → ddddddd...ddd (247 chars)
└─ b → ddddddd...ddd (247 chars)
   └─ c → ddddddd...ddd (247 chars)
      └─ ... (16 niveles, ~3952 chars en total)
         └─ final → /etc/sudoers.d/wacky (archivo privilegiado destino)

Cuando el filtro resuelve la cadena con os.path.realpath(), agota el MAX_PATH a mitad de la cadena y se detiene — sin llegar nunca al destino real. Lo considera válido y la extracción procede. En tiempo de ejecución, el kernel sigue la cadena de symlinks real y completa, y escribe en el archivo privilegiado.
